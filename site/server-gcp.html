Google Cloud で始める

プロジェクトと料金の通知から、Compute Engine のサーバーを作り、最初から開いている SSH を閉じ、鍵を置かずにバックアップを Cloud Storage へ送るところまで。終わったら どこでも同じ後半 へ進みます。

先に知っておく言葉

入れ物

プロジェクト

サーバーやファイルの置き場をまとめる単位。料金もプロジェクトごとに数えます。お店ごとに 1 つ作ります。

サーバー

Compute Engine と VM

Google Cloud で借りるサーバー。1 台を「VM インスタンス」と呼びます。

ファイアウォール

ファイアウォール ルール

サーバーに「誰が・どの番号の口から」入れるかの決まり。最初から入っているルールが SSH を世界中に開けているので、閉じます。

ファイルの置き場

Cloud Storage とバケット

ファイルを置く場所。1 つの置き場を「バケット」と呼びます。名前は世界中で重ならないものにします。

権限

サービス アカウント

サーバーに付ける「役割」。役割に「このバケットに書いてよい」と決めておくと、鍵のファイルを置かずにサーバーからバケットへ書けます。

場所

リージョン

サーバーを置く地域。日本のお店なら asia-northeast1（東京）。作るたびに選ぶので、毎回確かめます。

サーバーを作るまで

「サーバー」の札は、サーバーに効くコマンドの印です。ssh shop '…' の形のものは、パソコンのターミナルで打ちます。画面の項目名は 2026 年 11 月の日本語の管理画面（コンソール）のものです。名前が変わっていたら、何をしたいかで探してください。

A

アカウントとプロジェクト

サーバーより先に、Google アカウントとお金の見張りを固めます。

  1. ブラウザGoogle アカウントに二段階認証

    myaccount.google.com →「セキュリティ」→「2 段階認証プロセス」。パスキーか認証アプリを登録します。このアカウントが乗っ取られると、サーバーごと消されます。

  2. ブラウザお店用のプロジェクトを作る

    console.cloud.google.com → 上のプロジェクト名 →「新しいプロジェクト」→ 名前 myshop。以後、画面の上のプロジェクト名が myshop になっているのを確かめてから操作します。

  3. ブラウザ料金の通知を設定する

    「お支払い」→「予算とアラート」→「予算を作成」。対象のプロジェクト、金額（例: 月 10,000 円）、50%・90%・100% で通知。思ったより高いと気づけるのは、ここだけです。

  4. ブラウザサーバーの役割（サービス アカウント）を作る

    「IAM と管理」→「サービス アカウント」→「サービス アカウントを作成」→ 名前 myshop-server。「このサービス アカウントにプロジェクトへのアクセスを許可する」は何も選ばずに完了。権限はあとでバケットにだけ付けます。

B

VM を作る

Compute Engine →「VM インスタンス」（初回は「有効にする」を押して数分待ちます）→「インスタンスを作成」。左の項目を上から順に埋めます。

大きさの目安: 最低 2 vCPU・メモリ 4GB（PHP が 20 本で約 1.6GB、キャッシュの組み立てに 1GB、DB に 0.5GB を使います）。

  1. ブラウザマシンの構成

    名前 myshop、リージョン asia-northeast1（東京）、ゾーンはどれでも。シリーズ E2、マシンタイプ e2-medium（2 vCPU・4GB）。余裕を見るなら e2-standard-2（2 vCPU・8GB）。

  2. ブラウザOS とストレージ

    「変更」→ オペレーティング システム Ubuntu、バージョン「Ubuntu 24.04 LTS」（x86/64）。ディスクの種類「バランス永続ディスク」、サイズ 30 GB。ディスクは最初から暗号化されています。

  3. ブラウザネットワーキング

    「HTTP トラフィックを許可する」「HTTPS トラフィックを許可する」はチェックしません（公開は Tunnel で、外から入る口は要りません）。

  4. ブラウザセキュリティ

    「Shielded VM」→「セキュアブートをオンにする」にチェック。
    「ID と API へのアクセス」→ サービス アカウント myshop-server、アクセス スコープ「すべての Cloud API に完全アクセス権を許可」。
    「アクセスの管理」→「手動で生成した SSH 認証鍵を追加」→「項目を追加」→ 作った公開鍵（ssh-ed25519 AAAA… shop の 1 行）を貼ります。最後の shop がログインのユーザー名になります。

    アクセス スコープを既定のままにしない。既定は Cloud Storage を「読み取りのみ」に絞るので、あとでバケットに権限を付けても書けず、バックアップが送れません。「完全アクセス」にしても、できることはサービス アカウントに付けた権限（このあとバケットにだけ付けるもの）に限られます。

  5. ブラウザ詳細オプション

    「削除からの保護を有効にする」にチェック（誤ってサーバーを消せないように）。「作成」。

  6. ブラウザIP アドレスを固定する

    「VPC ネットワーク」→「IP アドレス」→ myshop の外部アドレスの行 →「静的アドレスに昇格」。しないと、止めて起動し直すたびに IP が変わります。サーバーを消したら、この IP も解放します（使っていない静的 IP にも料金がかかります）。

C

最初から開いている SSH を閉じる

新しいプロジェクトの default ネットワークには、最初からルールが 4 つ入っています。そのうち default-allow-ssh は22 番を世界中（0.0.0.0/0）に開けています。あなたの IP からだけに替えます。

先に自分のルールを足してから、古いルールを消す。逆にすると、その間あなたも入れなくなります（入れなくなっても、ルールを足し直せば戻ります）。

  1. パソコン自分の IP アドレスを調べる

    curl -s https://api.ipify.org

    198.51.100.23 のような数字が出ます。自宅やお店の回線の IP です（ときどき変わります）。

  2. ブラウザ自分からだけ入れるルールを足す

    「VPC ネットワーク」→「ファイアウォール」→「ファイアウォール ルールを作成」。名前 allow-ssh-from-me、ネットワーク default、トラフィックの方向「上り」、一致したときのアクション「許可」、ターゲット「ネットワーク上のすべてのインスタンス」、ソース IPv4 範囲 198.51.100.23/32（調べた IP の後ろに /32）、プロトコルとポート「TCP」22。

  3. ブラウザ世界中に開いているルールを消す

    同じ一覧で default-allow-ssh と default-allow-rdp（Windows 用の 3389 番。要りません）にチェック →「削除」。default-allow-icmp（ping）と default-allow-internal（ネットワークの中どうし）は残して構いません。

  4. パソコンIP が変わったら

    家の回線が変わって入れなくなったら、allow-ssh-from-me を開いてソース IPv4 範囲を新しい IP に書き換えます。

D

SSH で入れるようにする

パソコンに「shop と打てばこのサーバー」という呼び名を登録します。キットのコマンドはこの呼び名で動きます。

入れないときは OS Login を疑う。会社の Google Workspace などで「OS Login」が有効だと、貼った公開鍵は使われません。プロジェクトの「メタデータ」で enable-oslogin が TRUE になっていないかを見ます。

  1. パソコン呼び名を書く

    # ~/.ssh/config に足す（ファイルが無ければ作る）
Host shop
  HostName 203.0.113.10   # 固定した外部 IP
  User shop               # 公開鍵の最後に付けた名前
  IdentityFile ~/.ssh/id_ed25519

  2. パソコン入ってみる

    ssh shop

    初回は「この相手で合っているか」と聞かれるので yes。shop@myshop:~$ と出れば入れています。exit で抜けて、パソコンに戻ります（このあとのコマンドはパソコンで打ちます）。

  3. サーバーパスワードで入れないことを確かめる

    ssh shop 'sudo sshd -T | grep -E "^(passwordauthentication|permitrootlogin) "'

    passwordauthentication no と permitrootlogin without-password（または no）なら大丈夫です。yes と出たら、VPS のページの「SSH を固める」と同じ設定を入れます。

  4. サーバーOS の自動更新を確かめる

    ssh shop 'apt-config dump | grep -E "APT::Periodic::(Update-Package-Lists|Unattended-Upgrade) "'
ssh shop 'systemctl is-active apt-daily.timer apt-daily-upgrade.timer'

    1 行目の 2 つがどちらも "1"、2 行目が active 2 つなら、セキュリティ更新は毎日自動で入ります。違っていたら ssh -t shop 'sudo dpkg-reconfigure -plow unattended-upgrades'（「はい」）と ssh shop 'sudo systemctl enable --now apt-daily.timer apt-daily-upgrade.timer'。カーネルの更新は再起動するまで効かないので、月に 1 回、お客さんの少ない時間に ssh shop 'sudo reboot'（お店は自動で立ち上がります）。

E

バックアップの置き場（Cloud Storage）

サーバーの外にバックアップを置きます。サーバーには鍵を置かず、サービス アカウントに「このバケットに足してよい・読んでよい」とだけ許します。消す・上書きする権限は渡しません。サーバーが乗っ取られても、バックアップは消されません。

古いバックアップはバケットが消す。サーバーには消す権限が無いので、30 日たったらバケットの決まり（ライフサイクル）で消えるようにします。

  1. ブラウザバケットを作る

    「Cloud Storage」→「バケット」→「作成」。名前は世界で 1 つのもの（例: myshop-backup-7k2p）。ロケーション タイプ「Region」→ asia-northeast1（東京）。ストレージ クラス「Standard」。「このバケットに対する公開アクセス禁止を適用する」にチェック、アクセス制御「均一」。

  2. ブラウザ30 日で消える決まりを作る

    作ったバケット →「ライフサイクル」→「ルールを追加」→ アクション「オブジェクトを削除する」→ 条件「経過日数」30。

  3. ブラウザサービス アカウントに権限を付ける

    バケット →「権限」→「アクセス権を付与」→ 新しいプリンシパルに myshop-server@<プロジェクト ID>.iam.gserviceaccount.com。ロールは 2 つ:「Storage オブジェクト作成者」（足せる）と「Storage オブジェクト閲覧者」（一覧と読み取り）。「管理者」や「ユーザー」は付けません（消せてしまいます）。

  4. サーバーrclone を入れて、送り先を登録する

    ssh shop 'sudo apt-get install -y unzip && curl -fsSL https://rclone.org/install.sh | sudo bash'
ssh shop 'rclone config create gcsbackup "google cloud storage" env_auth=true bucket_policy_only=true'

    env_auth=true が「鍵の代わりにサーバーのサービス アカウントを使う」という意味です。bucket_policy_only=true は、アクセス制御を「均一」にしたバケットに要る設定です。

  5. パソコンあとは共通の手順で

    どこでも同じ後半の「バックアップを毎日取る」で bin/setup.sh backup を打ったら、「1) rclone」→ 送り先 gcsbackup → パス myshop-backup-7k2p/myshop と答えます。

F

メールの送り方

Google Cloud は、サーバーからのメールの 25 番を例外なく塞いでいます。注文メールは外の送信サービスから、587 番で送ります。

  1. ブラウザ送信サービスを選ぶ

    SendGrid・Resend・Amazon SES、または Google Workspace を使っているならその SMTP。送り元のドメインを、そのサービスの手順で確認（SPF / DKIM の DNS レコードを Cloudflare に足す。プロキシは「DNS のみ」）しておきます。

  2. パソコンキットに入れる

    bin/setup.sh mail --remote=shop:/srv/myshop

    サービスを選んで質問に答えると、試しに 1 通送ります。届いたものだけを書きます。

必要になったら足すもの

最初はなくても困りません。お店が育ってきたら足します。

商品画像をバケットから配る

  • Google Cloud だけで配るなら、画像用のバケットを公開にして、前に「外部アプリケーション ロードバランサ」と Cloud CDN を置きます。ロードバランサには、使っていなくても毎月の固定料金がかかります。
  • Cloudflare をもう使っているなら、画像は Cloudflare R2 に置くほうが簡単で安上がりです（配信の転送量がかかりません）。手順は 商品画像を S3 / R2 から配る。

DB を Cloud SQL（マネージド DB）にする

  • バックアップと故障時の切り替えを Google に任せられます。料金は上がります。
  • Cloud SQL には MariaDB がありません。MySQL 8 か PostgreSQL です。いまの DB（MariaDB）から MySQL 8 へ写すときは、先に検証環境で試してください。「パブリック IP」は使わず「プライベート IP」で繋ぎます。
  • 切り替えは bin/setup.sh db --remote=shop:/srv/myshop（繋がるか試して、いまのデータを写すかを聞きます）。

ディスクごとの控え（スナップショット）

  • Compute Engine →「スナップショット」→「スナップショット スケジュールを作成」（毎日、7 日保持）→ ディスクの「編集」でそのスケジュールを付けます。
  • サーバーごと壊れたときに丸ごと戻せます。お店のデータを戻すのは bin/backup.sh のほうが確実です。両方あると安心です。

止まったら知らせる

  • Google 側の機械の入れ替えでは、VM は止まらずに移されます（既定の設定）。
  • お店が開くかは外から見ます。Cloud Monitoring の「稼働時間チェック」か UptimeRobot で https://お店のドメイン/ を 5 分おきに。

やらないこと

  • サービス アカウントの鍵（JSON ファイル）を作ってサーバーに置く。漏れると、その鍵でできることが全部できてしまいます。VM にサービス アカウントを付ければ要りません。
  • default-allow-ssh を残す。世界中から総当たりで試されます。
  • バックアップのバケットを公開にする。会員の個人情報そのものです。
  • サービス アカウントにプロジェクト全体の「編集者」を付ける。付けるのはバケットへの 2 つのロールだけです。
次へ SSH で入れて、バックアップの置き場ができたら、どこでも同じ後半へ進みます（時刻を日本時間に → Docker とファイル → メール → Tunnel → 公開 → バックアップ）。
