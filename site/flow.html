開発から本番へ

パソコンで直して試し、GitHub に控えを置き、サーバーへ出す。お店に関わる場所は 3 つで、出し方は毎回同じです。このページでは、パソコンの中の開発環境と本番環境の作り方、直したものを安全に本番へ出す手順を、初めての人向けに順番に書きます。

お店に関わる3 つの場所

決まりは 1 つだけです。直すのはパソコン、動かすのはサーバー。サーバーの上では直しません。パソコンで直したものを GitHub に控え、そこからサーバーへ送ります。

  1. 1開発環境あなたのパソコン
    • 直して、試す場所。お店がまるごとパソコンの中で動きます（http://localhost:8080/）。
    • 壊しても誰にも迷惑がかかりません。お客さんは見ていません。
    • メールは外へ出ず、パソコンの中の受け箱（Mailpit）に届きます。試しに注文しても、誰にもメールは届きません。
  2. 2あなたのリポジトリGitHub（非公開）
    • 直したものの控え。いつ・誰が・何を直したかが残り、いつでも前の状態に戻せます。
    • 本番に出せるのは、ここの main に入ったものだけです。
  3. 3本番環境借りたサーバー
    • お客さんが買い物をする場所。ここでは直しません。bin/deploy.sh で送られてきたものを動かすだけです。
    • サーバーに git も GitHub の鍵も置きません。お店のファイルは、あなたのパソコンから送ります。
ステージング（本番そっくりの確認用の環境）は？ 小さなお店・中くらいのお店なら、いつも置いておく必要はありません。パソコンの開発環境も本番と同じモードで動くので、パソコンで動けば本番でもたいてい同じように動きます。EC-CUBE そのものを上げるときだけは、パソコンの別のフォルダに確認用を作り、本番のバックアップを戻して試してから本番で上げます（EC-CUBE のバージョンアップ）。終わったら消してかまいません。

開発環境を作る

最初に 1 回だけです。終わると、パソコンのブラウザでお店と管理画面が開きます。

パソコン

Mac か Windows

Mac は最初から入っている「ターミナル」を使います。Windows は WSL2（Ubuntu）を入れ、その中で打ちます。コマンドは bash 用で、PowerShell では動きません。

お店を動かす台

Docker Desktop

公式サイトから入れて、起動しておきます。お店は、この中の箱（コンテナ）で動きます。

控えの置き場

GitHub のアカウントと gh

GitHub のアカウントを作り、二段階認証を有効にします。gh は GitHub をコマンドで扱う道具です（Mac なら brew install gh）。

A

パソコンでお店を動かす

上から順に打ちます。myshop は好きな名前に変えてかまいません。

時間: 10 分ほど（動かすところは数十秒）。

git clone はしません。キットを clone すると、控えの送り先がキットの配布元のままになります。中身だけをもらって、あなた専用の非公開リポジトリにします。

  1. パソコンGitHub にログインする

    gh auth login

    質問に答えると、ブラウザで GitHub のログイン画面が開きます。1 回だけです。

  2. パソコンキットの中身をもらう

    curl -fsSL https://github.com/kurozumi/eccube-kit/releases/latest/download/eccube-docker.tar.gz | tar -xz
mv eccube-docker-* myshop && cd myshop

    いつも最新のリリースが落ちてきます。

  3. パソコンあなたの非公開リポジトリにする

    git init -b main && git add -A && git commit -m "eccube-kit から開始"
gh repo create myshop --private --source=. --push

    --private を必ず付けます。これが「あなたのリポジトリ」です。

  4. パソコンお店を動かす

    bin/init.sh --image=ghcr.io/kurozumi/eccube-kit/ec-cube:4.3-php8.3

    パスワード類を作り、空いているポートを選び、お店を起動して、終わるまで待ちます。4.3 が EC-CUBE の版、php8.3 が PHP の版です。最後にお店の URL・管理画面の URL・ログイン ID・パスワードが出るので、控えておきます。

  5. ブラウザ開いてみる

    開くものURL使いみち
    お店http://localhost:8080/お客さんから見える画面
    管理画面http://localhost:8080/admin-<乱数>/手順 4 で出た URL。商品や注文を扱う
    メールの受け箱http://localhost:8025/お店が送ったメールがここに届く（外へは出ない）
    DB の画面http://localhost:8081/データベースの中身を見る（開発環境にだけある）

    ほかのソフトが番号を使っていたときは、bin/init.sh が空いている番号を選び、実際の URL を表示します。

A2

2 台目のパソコン・2 人目の人

もうリポジトリがあるなら、キットの中身はもらいません。あなたのリポジトリを clone します。

  1. パソコンあなたのリポジトリを取ってきて動かす

    gh repo clone <持ち主>/myshop && cd myshop
bin/init.sh --image=ghcr.io/kurozumi/eccube-kit/ec-cube:4.3-php8.3

    <持ち主> は、リポジトリを作った人の GitHub のユーザー名です（自分で作ったなら自分の名前）。省くと、打った人のアカウントの myshop を探すので、ほかの人が作ったリポジトリは取れません。2 人目の人は、先に持ち主から GitHub でリポジトリに招待してもらいます。--image= は本番と同じものにします（本番の .env の ECCUBE_IMAGE）。.env は git に入らないので、パソコンごとに新しく作られます。お店の中身は最初の空の状態で、本番のお客さんや注文は入っていません。

本番環境を作る

サーバーを借りて、SSH で入れるようにしたら、あとはパソコンからコマンドを順に打つだけです。サーバーに入って作業することはほとんどありません。

B

サーバーにお店を載せる

時間: サーバーを借りるところを除いて 30 分ほど。

サーバーに git は置きません。お店のファイルはパソコンから送ります。サーバーに GitHub の鍵を置かずに済みます。

  1. ブラウザサーバーを借りて、守りを固める

    VPS・AWS・Google Cloud のどれでもかまいません。借り方、SSH の鍵、ファイアウォールは 本番サーバーを用意する に、画面の操作から書いてあります。終わると、パソコンから ssh shop でサーバーに入れるようになります（shop は ~/.ssh/config に書いたサーバーの呼び名）。

  2. サーバーDocker を入れて、お店のファイルを送る（パソコンから打つ）

    bin/bootstrap-server.sh shop /srv/myshop

  3. サーバーメールと公開の設定（パソコンから打つ）

    bin/setup.sh mail   --remote=shop:/srv/myshop
bin/setup.sh tunnel --remote=shop:/srv/myshop

    質問に答えるだけです。メールは 1 通試してから、公開は Cloudflare に繋がるか試してから書きます。

  4. サーバー公開する（パソコンから打つ）

    bin/publish.sh --remote=shop:/srv/myshop

  5. サーバー毎日のバックアップを入れる（パソコンから打つ）

    bin/setup.sh backup --remote=shop:/srv/myshop

    暗号化して、サーバーの外へ毎日送ります。表示された暗号化の鍵と、サーバーの .env の中身をパスワードマネージャに控えます。失くすと二度と戻りません。

それぞれの手順の細かいところと、公開の前に確かめることは 本番サーバーを用意する にあります。

直したものを本番へ出す

毎回この 6 つの順番です。どれも、あなたのパソコンで打ちます。慣れたら 1 と 2 を繰り返し、まとまったら 3 から先へ進みます。

C

いつもの出し方

時間: 出すところ（5）は数分。お客さんには、そのあいだ「メンテナンス中」が出ます。

お客さんの少ない時間に出します。メンテナンス表示が出るあいだは注文ができません。ログイン中の管理者は、そのあいだも管理画面に入れます。

  1. パソコン直す

    直したいもの触る場所
    見た目（CSS）frontend/scss/customize.scss を直して bin/assets.sh build
    画面の部品（テンプレート）app/template/original/ に、直すファイルだけを置く
    プラグインの画面・メールの文面bin/plugin.sh template add <プラグイン> <ファイル> で写してから直す
    動き（PHP）app/Customize/

    EC-CUBE そのもののファイルは直しません。上げたときに消えるか、古いほうが残り続けるからです。

  2. ブラウザパソコンで確かめる

    http://localhost:8080/ を開いて、直したところと、その周りを触ってみます。メールが関わるなら、メールの受け箱（http://localhost:8025/）で届いた文面を見ます。直したのに変わらないときは bin/plugin.sh reload。

  3. パソコン控えを送る

    git add -A
git commit -m "何を直したか"
git push

    -m のあとには、あとで読んで分かる言葉を書きます（「送料無料の金額を 5,000 円に」など）。本番に出すときに、この一覧が出ます。

  4. パソコン何が出るかを見る

    bin/deploy.sh --check --remote=shop:/srv/myshop

    まだ何も変えません。出るコミットの一覧と、気をつけるもの（データベースの形が変わる、など）が出ます。思っていたものと違えば、ここで止めます。

  5. サーバー出す（パソコンから打つ）

    bin/deploy.sh --remote=shop:/srv/myshop

    もう一度一覧が出て、プロジェクト名を打つように言われます。y では進みません。打つ前なら、何も変わっていません。打つと、次のことを順に自動でやります。

    いまの状態を退避 → メンテナンス表示 → ファイルを送る → データベースを新しい形に → キャッシュを組み立て直す → 画面が開くかを確かめる → メンテナンス表示を外す

    途中で止めないでください（Ctrl-C を押さない、ターミナルを閉じない）。キャッシュの組み立ての途中で止めると、全部のページがエラーになります。

  6. ブラウザ本番を目で確かめる

    トップ・商品のページ・カートに入れる・管理画面にログイン・受注一覧。直したところも開きます。

プラグインは別の扱い プラグインは、既定では git に入りません（買ったものはそれぞれの提供元のもの、という考え）。なので bin/deploy.sh では本番に届きません。どう届けるか（本番にも入れる・git に入れて一緒に管理する）は、最初に決めておきます（導入手順）。パソコンで入れるのは bin/plugin.sh add <URL> です。

うっかりはキットが止める

本番に出す前に、bin/deploy.sh が次のことを確かめます。どれかに当たると何も送らずに止まり、何が悪いかを日本語で出します。

うっかりキットがすること
コミットしていない作りかけの変更がある送らない。作りかけが本番に出ない
試しに作った別のブランチにいる送らない。本番に出せるのは main だけ
git push を忘れた／パソコンの main が古い送らない。GitHub の main の先頭とまったく同じものしか出せない
何が出るか見ないまま出そうとした一覧を見せて、プロジェクト名を打つまで進まない。誰が・いつ・何を出したかをサーバーに記録する
出している途中で失敗したメンテナンス表示のまま止まり、壊れた画面をお客さんに見せない。戻し方を表示する
本番の管理画面で直したものを、パソコンの古い版で上書きしそう（下）送らない。どのファイルかと、取り込み方を出す
何人かで運用するなら 直す人と出す人を分け、GitHub で「承認が無いと main に入らない」ようにできます（bin/setup.sh protect）。本番の SSH は出す人だけが持ちます。詳しくは 本番には、レビュー済みの main しか出ない。

管理画面で直したものはサーバーにしか無い

管理画面の「CSS 管理」「ページ管理」「ブロック管理」「メール設定」の本文は、本番サーバーのファイルに書かれます。あなたのパソコンにも GitHub にも、自動では入りません。毎日のバックアップには入るので消えはしませんが、控えに残すには取り込みます。

D

本番の管理画面で直した分を、控えに入れる

本番の管理画面で直したものがあると、bin/deploy.sh は何も送らずに止まり、どのファイルかを出します（送ると、パソコンの古い版で上書きして消してしまうため）。そうなったら、これをやってから出し直します。止まる前でも、管理画面で直したら早めに取り込んでおくと安心です。

  1. パソコンサーバーから取り込んで、控えを送る

    bin/pull-admin-files.sh shop:/srv/myshop
git add app/template html/user_data
git commit -m "管理画面で直した分を取り込む" && git push

    見た目やテンプレートを直すのは、なるべくパソコンのほう（直したものを本番へ出す）に寄せます。管理画面とパソコンの両方で同じものを直すと、どちらが正しいか分からなくなります。

出したあとでおかしいと気づいたら

慌てて本番のファイルを直接書き換えないでください。次の順に試します。

E

上から順に試す

1 で直ればそこで終わりです。直らなければ 2、データベースまで戻すのは 3 です。

出す直前の状態は、いつも取ってあります。bin/deploy.sh は、メンテナンス表示を立ててからファイルを入れ替える前に、サーバーの backups/<日時>-before-deploy/ へ退避しています。上書きした前のファイルは var/deploy-prev/<日時>/ にも残ります。

  1. サーバーまず点検する

    ssh shop
cd /srv/myshop
bin/plugin.sh doctor

    残骸の掃除、キャッシュの組み立て直し、主なページが開くかの確認までやります。何が悪いかが日本語で出るので、そのとおりにします。「メンテナンス中」のまま残ったときも、これで外れます。

  2. パソコン直したものを取り消して、出し直す

    git revert --no-edit HEAD
git push
bin/deploy.sh --remote=shop:/srv/myshop

    直前のコミットを打ち消すコミットを作り、いつもどおり出します。履歴は消えず、「取り消した」ことも残ります。GitHub の PR でマージしたものなら、PR の画面の「Revert」ボタンで取り消しの PR を作り、マージしてから出し直しても同じです。

  3. サーバーデータベースも戻す

    ssh shop
cd /srv/myshop
bin/restore.sh backups/<日時>-before-deploy

    データベースの形を変える変更を出したあとだけです。2 でコードを戻してから、おかしくなった deploy の直前の退避から戻します。2 で出し直したときにも新しい退避ができるので、ls backups で日時を見て、古いほうを選びます。

    退避のあとに入った注文や、管理画面で変えたものは消えます。いちばん重い操作なので、戻す前に受注一覧でその時刻からの注文を確かめ、迷ったら打つ前に詳しい人に相談してください。

本番でやらないこと

サーバーの上で直す

  • サーバーのファイルを直接書き換えると、控えに残りません。次に出したときに、パソコンの中身で上書きされるか、出せなくなります。
  • 直すのはいつもパソコンで、出すのはいつも bin/deploy.sh です。

消えるコマンドを打つ

  • bin/reset.sh・bin/switch-version.sh・docker compose down -v は、データベースと画像を消します。本番では打ちません。
  • 本番で打とうとすると止まるようになっていますが、止まるのを当てにしないでください。

途中で止める

  • bin/deploy.sh や bin/upgrade.sh の途中で Ctrl-C を押したり、ターミナルを閉じたりしない。
  • 動いていないように見えても、キャッシュを組み立てているあいだは数分かかります。

本番の SSH をみんなに渡す

  • 本番の SSH を持つ人は、キットの確かめを通らずにファイルを置けます。
  • 持つのは出す人だけにします。
正直に キットが止められるのは「うっかり」までです。止まる仕組みは、パソコンとサーバーのあいだ（bin/deploy.sh）に入っています。サーバーに SSH で入って直接ファイルを置くことは止められません。また、EC-CUBE そのものを上げるのは bin/deploy.sh ではなく bin/upgrade.sh です（EC-CUBE のバージョンアップ）。
