AWS で始める

AWS のアカウントを守るところから、EC2 のサーバーを作り、鍵を置かずにバックアップを S3 へ送るところまで。終わったら どこでも同じ後半 へ進みます。

先に知っておく言葉

サーバー

EC2

AWS で借りるサーバー（仮想マシン）。1 台を「インスタンス」と呼びます。

ファイアウォール

セキュリティグループ

サーバーに「誰が・どの番号の口から」入れるかの決まり。ここに書いていない通信は全部断られます。

ファイルの置き場

S3 とバケット

ファイルを置く場所。1 つの置き場を「バケット」と呼びます。名前は世界中で重ならないものにします。

権限

IAM ロール

サーバーに付ける「役割」。役割に「このバケットに書いてよい」と決めておくと、鍵のファイルを置かずにサーバーから S3 へ書けます。

固定の住所

Elastic IP

サーバーに付ける変わらない IP アドレス。付けないと、止めて起動し直すたびに IP が変わり、SSH の行き先を書き直すことになります。

場所

リージョン

サーバーを置く地域。日本のお店ならアジアパシフィック（東京）ap-northeast-1。画面の右上でいつも確かめます（ほかの地域で作ると、見つからなくなります）。

サーバーを作るまで

「サーバー」の札は、サーバーに効くコマンドの印です。ssh shop '…' の形のものは、パソコンのターミナルで打ちます。画面の項目名は 2026 年 11 月の日本語の管理画面のものです。名前が変わっていたら、何をしたいかで探してください。

A

アカウントを守る

サーバーより先に、AWS のアカウントそのものを守ります。乗っ取られると、高いサーバーを大量に立てられて、請求があなたに来ます。

ルートユーザーはふだん使わない。登録したメールアドレスで入るのがルートユーザーで、何でもできてしまいます。二段階認証をかけたら、しまっておきます。

  1. ブラウザルートユーザーに二段階認証（MFA）

    右上のアカウント名 →「セキュリティ認証情報」→「MFA を割り当てる」。スマートフォンの認証アプリか、パスキーを登録します。

  2. ブラウザふだん使う管理ユーザーを作る

    IAM →「ユーザー」→「ユーザーの作成」。名前（例: admin-yourname）、「AWS マネジメントコンソールへのユーザーアクセスを提供する」にチェック。許可は「ポリシーを直接アタッチする」→ AdministratorAccess。作ったら、このユーザーにも MFA を割り当て、以後はこのユーザーで入ります。

  3. ブラウザ料金の通知を設定する

    「請求とコスト管理」→「予算」→「予算を作成」→ テンプレート「月次コスト予算」。金額（例: 月 10,000 円ぶんの USD）と通知先のメールを入れます。思ったより高いと気づけるのは、ここだけです。

B

EC2 のサーバーを作る

右上のリージョンが「東京」になっているのを確かめてから、EC2 →「インスタンスを起動」。上から順に埋めます。

大きさの目安: 最低 2 vCPU・メモリ 4GB（PHP が 20 本で約 1.6GB、キャッシュの組み立てに 1GB、DB に 0.5GB を使います）。商品やアクセスが多いなら 8GB。

  1. パソコン公開鍵を AWS に登録する

    先に EC2 →「キーペア」→「アクション」→「キーペアをインポート」。名前（例: shop）を付け、作った公開鍵（~/.ssh/id_ed25519.pub の中身）を貼ります。AWS に鍵を作らせて .pem をダウンロードするやり方より、秘密鍵がパソコンの外に出ないぶん安全です。

  2. ブラウザ名前と OS

    名前: myshop。「アプリケーションおよび OS イメージ」→ Ubuntu →「Ubuntu Server 24.04 LTS」。アーキテクチャは「64 ビット (Arm)」にすると同じ性能で安くなります（キットは Arm でも動きます）。

  3. ブラウザインスタンスタイプ

    Arm なら t4g.medium（2 vCPU・4GB）、余裕を見るなら t4g.large（2 vCPU・8GB）。x86 を選んだなら t3.medium / t3.large。

  4. ブラウザキーペア

    さっき登録した shop を選びます。

  5. ブラウザネットワーク設定（いちばん大事）

    「セキュリティグループを作成」。「からの SSH トラフィックを許可」にチェックし、右の選択を「自分の IP」に。「インターネットからの HTTPS トラフィックを許可」「インターネットからの HTTP トラフィックを許可」はチェックしません（公開は Tunnel で、外から入る口は要りません）。

  6. ブラウザストレージ

    30 GiB、種類は gp3。「詳細」を開いて「暗号化済み」を「暗号化」に（ディスクを盗まれても読めません）。

  7. ブラウザ高度な詳細

    「終了保護」→「有効化」（誤ってサーバーを消せないように）。「メタデータのバージョン」→「V2 のみ (トークンは必須)」。「メタデータのレスポンスホップ制限」→ 2（Docker の中の rclone が、サーバーの役割を使えるように。1 のままだとコンテナの中から届きません）。

  8. ブラウザ起動して、固定の IP を付ける

    「インスタンスを起動」。次に EC2 →「Elastic IP」→「Elastic IP アドレスを割り当てる」→ 割り当てたものを選んで「アクション」→「Elastic IP アドレスの関連付け」→ さっきのインスタンス。IP アドレスは、使っていてもいなくても少し料金がかかります。サーバーを消したら、IP も「解放」します（残すと料金だけかかり続けます）。

C

SSH で入れるようにする

パソコンに「shop と打てばこのサーバー」という呼び名を登録します。キットのコマンドはこの呼び名で動きます。

Ubuntu のサーバーのユーザー名は ubuntu。最初からパスワードでは入れず、鍵だけで入れる設定になっています。

  1. パソコン呼び名を書く

    # ~/.ssh/config に足す（ファイルが無ければ作る）
Host shop
  HostName 203.0.113.10   # Elastic IP
  User ubuntu
  IdentityFile ~/.ssh/id_ed25519

  2. パソコン入ってみる

    ssh shop

    初回は「この相手で合っているか」と聞かれるので yes。ubuntu@ip-…:~$ と出れば入れています。exit で抜けて、パソコンに戻ります（このあとのコマンドはパソコンで打ちます）。

  3. サーバーパスワードで入れないことを確かめる

    ssh shop 'sudo sshd -T | grep -E "^(passwordauthentication|permitrootlogin) "'

    passwordauthentication no と permitrootlogin without-password（または no）なら大丈夫です。yes と出たら、VPS のページの「SSH を固める」と同じ設定を入れます。

  4. サーバーOS の自動更新を確かめる

    ssh shop 'apt-config dump | grep -E "APT::Periodic::(Update-Package-Lists|Unattended-Upgrade) "'
ssh shop 'systemctl is-active apt-daily.timer apt-daily-upgrade.timer'

    1 行目の 2 つがどちらも "1"、2 行目が active 2 つなら、セキュリティ更新は毎日自動で入ります。違っていたら ssh -t shop 'sudo dpkg-reconfigure -plow unattended-upgrades'（「はい」）と ssh shop 'sudo systemctl enable --now apt-daily.timer apt-daily-upgrade.timer'。カーネルの更新は再起動するまで効かないので、月に 1 回、お客さんの少ない時間に ssh shop 'sudo reboot'（お店は自動で立ち上がります）。

D

バックアップの置き場（S3）

サーバーの外にバックアップを置きます。サーバーには鍵を置かず、サーバーの役割（IAM ロール）に「このバケットに足してよい・読んでよい」とだけ許します。消す権限は渡しません。サーバーが乗っ取られても、バックアップは消されません。

古いバックアップは S3 が消す。サーバーには消す権限が無いので、30 日たったら S3 の決まり（ライフサイクル）で消えるようにします。

  1. ブラウザバケットを作る

    S3 →「バケットを作成」。名前は世界で 1 つのもの（例: myshop-backup-7k2p）。リージョンは東京。「パブリックアクセスをすべてブロック」はオンのまま。「バケットのバージョニング」→「有効にする」（上書きされても前の版が残ります）。暗号化は既定（SSE-S3）のまま。

  2. ブラウザ30 日で消える決まりを作る

    作ったバケット →「管理」→「ライフサイクルルールを作成する」。範囲は「バケット内のすべてのオブジェクトに適用」。「オブジェクトの現行バージョンを有効期限切れにする」→ 30 日、「オブジェクトの非現行バージョンを完全に削除」→ 30 日、「期限切れのオブジェクト削除マーカーまたは不完全なマルチパートアップロードを削除」→「不完全なマルチパートアップロードを削除」→ 7 日（大きなバックアップを送っている途中で止まると、送りかけの断片が残り、見えないまま料金がかかり続けます）。

  3. ブラウザサーバーの役割（IAM ロール）を作る

    IAM →「ロール」→「ロールを作成」→「AWS のサービス」→ ユースケース「EC2」→ 許可ポリシーは何も選ばずに次へ → 名前 myshop-server で作成。作ったロール →「許可を追加」→「インラインポリシーを作成」→「JSON」に下を貼り、バケット名を自分のものに替えます。

    {
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow",
      "Action": ["s3:ListBucket"],
      "Resource": "arn:aws:s3:::myshop-backup-7k2p" },
    { "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:GetObject"],
      "Resource": "arn:aws:s3:::myshop-backup-7k2p/*" }
  ]
}

    DeleteObject が無いのが要点です（足すだけで、消せません）。

  4. ブラウザサーバーに役割を付ける

    EC2 →「インスタンス」→ myshop を選ぶ →「アクション」→「セキュリティ」→「IAM ロールを変更」→ myshop-server。

  5. サーバーrclone を入れて、送り先を登録する

    ssh shop 'sudo apt-get install -y unzip && curl -fsSL https://rclone.org/install.sh | sudo bash'
ssh shop 'rclone config create s3backup s3 provider=AWS env_auth=true region=ap-northeast-1 no_check_bucket=true'

    env_auth=true が「鍵の代わりにサーバーの役割を使う」という意味です。no_check_bucket=true は、バケットを作ろうとしない設定です（その権限も渡していないため）。

  6. パソコンあとは共通の手順で

    どこでも同じ後半の「バックアップを毎日取る」で bin/setup.sh backup を打ったら、「1) rclone」→ 送り先 s3backup → パス myshop-backup-7k2p/myshop と答えます。

E

メールを Amazon SES で送る

ほかの送信サービス（SendGrid・Resend など）を使うなら、この節は飛ばして構いません。SES は安いかわりに、最初は「確認したアドレスにしか送れない」状態（サンドボックス）から始まります。

EC2 からの直接の送信（25 番）は使わない。AWS は最初から 25 番を絞っていて、送れても迷惑メールに入ります。SES の 587 番を使います。

  1. ブラウザ送り元のドメインを確認する

    Amazon SES（リージョンは東京）→「ID」→「ID の作成」→「ドメイン」に example.com。「Easy DKIM」のまま作ると、DNS に足す CNAME が 3 つ出ます。Cloudflare の DNS に 3 つとも足します。プロキシは「DNS のみ」（灰色の雲）に（オレンジのままだと確認が通りません）。

  2. ブラウザ本番で使えるように申請する

    SES の「アカウントダッシュボード」→「本番アクセスをリクエスト」。用途は「トランザクション」、ウェブサイトの URL、どんなメールを送るか（注文の確認・発送の連絡・会員登録の確認）を書きます。通るまで、確認していない相手には届きません。

  3. ブラウザSMTP の認証情報を作る

    SES →「SMTP 設定」→「SMTP 認証情報の作成」。出てきたSMTP ユーザー名とパスワードを控えます（IAM のアクセスキーとは別物です）。

  4. パソコンキットに入れる

    bin/setup.sh mail --remote=shop:/srv/myshop

    「2) Amazon SES」→ リージョン ap-northeast-1 → 控えたユーザー名とパスワード。試しに 1 通送って、届いたものだけを書きます。

必要になったら足すもの

最初はなくても困りません。お店が育ってきたら足します。

商品画像を S3 と CloudFront から配る

  • 画像用に、バックアップとは別のバケットを作ります（パブリックアクセスはブロックのまま）。
  • CloudFront →「ディストリビューションを作成」→ オリジンにそのバケット →「オリジンアクセス」は「Origin access control settings (recommended)」。表示されるバケットポリシーを、バケットの「アクセス許可」に貼ります。バケットを公開せずに、CloudFront からだけ読めるようになります。
  • ロールのインラインポリシーに、画像のバケットへの ListBucket・PutObject・GetObject を足します。写し方と URL の切り替えは 商品画像を S3 / R2 から配る。鍵の代わりに RCLONE_CONFIG_IMG_ENV_AUTH=true と PROVIDER=AWS・REGION=ap-northeast-1 を書きます。URL は https://dxxxx.cloudfront.net/save_image。

DB を RDS（マネージド DB）にする

  • バックアップと故障時の切り替えを AWS に任せられます。料金は上がります。
  • エンジンは MariaDB 10.11（いまの DB と同じ種類）。「パブリックアクセス」はなし。セキュリティグループは「3306 番を、EC2 のセキュリティグループからだけ」許可します。
  • 切り替えは bin/setup.sh db --remote=shop:/srv/myshop（繋がるか試して、いまのデータを写すかを聞きます）。

ディスクごとの控え（スナップショット）

  • EC2 →「Lifecycle Manager」→ ポリシーを作成 → 対象のディスク、毎日、7 世代。
  • サーバーごと壊れたときに丸ごと戻せます。ただし動いている DB をそのまま撮るので、お店のデータを戻すのは bin/backup.sh のほうが確実です。両方あると安心です。

止まったら知らせる

  • サーバーの故障は、EC2 が自動で別の機械へ移します（自動復旧は最初から有効）。
  • お店が開くかは外から見ます。UptimeRobot などで https://お店のドメイン/ を 5 分おきに。

やらないこと

  • アクセスキー（AKIA…）をサーバーに置く。漏れると、そのキーでできることが全部できてしまいます。サーバーにはロールを付けます。
  • セキュリティグループで 22 番を「0.0.0.0/0」（どこからでも）にする。世界中から総当たりで試されます。自宅の IP が変わったら、ルールのほうを書き換えます。
  • S3 のバケットを公開にする。バックアップは会員の個人情報そのものです。画像も CloudFront からだけ読ませます。
次へ SSH で入れて、バックアップの置き場ができたら、どこでも同じ後半へ進みます（時刻を日本時間に → Docker とファイル → メール → Tunnel → 公開 → バックアップ）。
