# セキュリティ対策

EC-CUBE 公式の「[EC-CUBE セキュリティ対策ガイドライン](https://www.ec-cube.net/security/guideline/)」（サイト運営者向け）の
項目ごとに、**キットが最初から満たしているもの**と**お店がやること**を並べます。ガイドラインは
「効果が高い対策の一覧で、防御を保証するものではない」としています。ここも同じです。

## 早見表

| 区分 | ガイドラインの対策 | キット | お店がやること |
|---|---|---|---|
| 入口 | WAF の導入 | 公開方式が `tunnel` なら Cloudflare を通る | [1. WAF と国の制限](#1-waf-と国の制限cloudflare) を設定する |
| 入口 | オリジンへの直接アクセスを拒否 | `tunnel` は開いたポートが無いので満たす | `caddy` で公開しているなら `tunnel` を考える |
| 入口 | 重要な場所にレート制限 | ログインとパスワード再発行は nginx で 1 分に 10 回ほど | 問い合わせ・会員登録は Cloudflare で足す |
| 入口 | 海外 IP の拒否 | なし | [1. WAF と国の制限](#1-waf-と国の制限cloudflare) |
| 内部 | ログ監視 | `bin/security.sh check`（管理画面のログイン・nginx のログ） | 毎日流して、要確認を見る |
| 内部 | 不審なデータの確認 | `bin/security.sh check`（管理者・会員・注文・ページ・プラグイン・git に無い変更） | 同上 |
| 内部 | AI によるログ分析 | ログを外へ出す手順だけ（[監視](monitoring.md)） | [3. 見張るもの](#3-見張るもの) の注意を守って使う |
| アプリ | 管理画面の IP 制限（IPv4 と IPv6） | 本体の機能を `.env.app` で使う | [2. 管理画面を守る](#2-管理画面を守る) |
| アプリ | 管理画面の全アカウントで MFA | 本体の 2 段階認証（既定で使える） | 全員を ON にする |
| アプリ | AI による脆弱性診断 | なし | [4. 自分のコードを AI で診断する](#4-自分のコードを-ai-で診断する) |
| アプリ | 不要データ・使っていないプラグインの削除 | `bin/plugin.sh doctor` が無効なプラグインを挙げる | `bin/plugin.sh remove` |
| アプリ | OS・ミドルウェア・ライブラリの最新化 | 毎日の焼き直しと点検（[ミドルウェアの脆弱性](security-updates.md)） | `bin/deploy.sh` を流す。本体のパッチは `bin/upgrade.sh` |
| 人的 | 標的型攻撃の教育 | 対象外 | ガイドラインのとおり |
| 兆候 | 閉じる・専門家に連絡・調査が終わるまで開けない | `bin/security.sh close` / `open` | [5. 不審な兆候が見えたら](#5-不審な兆候が見えたら) |

## 1. WAF と国の制限（Cloudflare）

ガイドラインは WAF に Cloudflare を勧めています。**公開方式が `tunnel` なら、お客さんの通信は全部 Cloudflare を
通ります。** サーバーにはポートが開いていないので、「オリジンへの直接アクセスを拒否する」もそれで満たします。
`caddy` はサーバーが直接受けるので、WAF を前に置くなら `tunnel` に変えるのがいちばん手が少ないです
（[導入手順](install.md)の公開方式）。

設定は Cloudflare のダッシュボードで、そのドメインの「セキュリティ」から行います。画面の名前は変わることがあります。

1. **標準のルールを有効にする。** 「WAF → マネージドルール」。無料プランでも Cloudflare の無料のルールが入ります。
   自分でルールを組まず、まず標準のまま使います。
2. **国で絞る。** 「WAF → カスタムルール」に 1 本足します。越境 EC でなければ日本以外を止め、
   **検索エンジンと AI の巡回は通します**（止めると検索結果に出なくなります）。
   ```
   (ip.src.country ne "JP" and not cf.client.bot and not starts_with(http.request.uri.path, "/<決済の通知の URL>"))
   ```
   動作は、最初は「マネージドチャレンジ」にして数日ようすを見て、問題が無ければ「ブロック」にします。
   **決済サービスからの通知（注文の確定を知らせる、サーバーからサーバーへの通信）は止めないこと。**
   通知元が海外のサービスもあり、止めると支払いが済んだのに注文が確定しません。通知の URL は決済プラグインの説明書にあります。
   国で絞るのは IPv4 も IPv6 も同じルールで効きます。
3. **レート制限を足す。** 「WAF → レート制限ルール」。ログインとパスワード再発行はキットの nginx がすでに
   IP ごとに 1 分に 10 回ほどに絞っています。残りの、問い合わせ（`/contact`）と会員登録（`/entry`）を IP ごとに絞ります。
   無料プランで作れるのは 1 本なので、この 2 つをまとめます。
4. **運用する。** 「セキュリティ → イベント」で止めたものを週に 1 回見ます。お客さんが止まっていれば緩め、
   攻撃が続いていれば強めます。

**Cloudflare で HTML をキャッシュする設定（Cache Everything）にはしないこと。** カートやログインの入った画面を、ほかの
お客さんに配ってしまいます。

## 2. 管理画面を守る

### IP 制限

管理画面に入れる IP を、お店の回線だけにします。**`.env.app` に書きます**（無ければ作る。git には入りません）。

```bash
echo 'ECCUBE_ADMIN_ALLOW_HOSTS=["203.0.113.10","2001:db8:1234::/48"]' >> .env.app
bin/publish.sh                      # 本番。開発なら docker compose up -d
```

- **IPv4 と IPv6 の両方を書く。** 許可の一覧なので、書かなかったほうからは入れなくなります。お店のパソコンが
  IPv6 で繋いでいると、IPv4 だけを書いた時点で自分が締め出されます。いまの自分の IP は、お店の URL の
  `/cdn-cgi/trace` を開くと `ip=` の行に出ます（`tunnel` のとき。EC-CUBE に届く IP と同じです）。
- 範囲で書くなら CIDR（`203.0.113.0/24`）。プロバイダの IPv6 は `/48` か `/56` で配られることが多いので、
  1 つのアドレスではなく範囲で書きます。広く取りすぎないこと。
- **管理画面の「セキュリティ管理」では設定しない。** 画面の値はコンテナの中の `.env` に書かれ、`bin/upgrade.sh` で
  本体を入れ替えると消えます。さらに、`.env.app` と両方にあると、4.2・4.3 は画面の値、4.4 は `.env.app` の値が勝ち、
  系列で効くほうが違います（4.4 は画面に「上書きされている」と出ます）。画面で 1 つのアドレスとして IPv6 を入れると
  「IPv4 アドレスではありません」と弾かれるのも本体の仕様で、`/128` を付けると通ります。

**締め出されたら**、サーバーで `.env.app` からその行を消して `bin/publish.sh` を打ち直します。4.2・4.3 で、
以前に画面からも入れていたなら、コンテナの中の値も消します。

```bash
docker compose exec ec-cube sed -i '/^ECCUBE_ADMIN_ALLOW_HOSTS=/d' /var/www/html/.env
```

管理画面の URL は、`bin/init.sh` が `admin-<乱数>` にしています。推測されにくい URL は探されにくいだけで、
IP 制限の代わりにはなりません。

### 2 段階認証（MFA）

ガイドラインは**管理画面の全アカウント**で求めています。本体の機能で、4.2・4.3・4.4 とも最初から使えます
（`ECCUBE_2FA_ENABLED` の既定が 1。0 にしないこと）。

1. 管理画面の「設定 → システム設定 → メンバー管理」で、メンバーごとに「2段階認証」を ON にする
2. そのメンバーが次にログインすると、認証アプリ（Google Authenticator など）の登録を求められる
3. 登録した端末とブラウザは 14 日間覚えられ、そのあいだはコードを聞かれません（`ECCUBE_2FA_EXPIRE`）

ON にしたのに登録が済んでいないメンバーは、そのメンバーの編集画面に「2段階認証の設定が未完了です」と出ます。

## 3. 見張るもの

ガイドラインが監視を勧めているのは次のものです。

- **ログ**
  - 管理画面へのログイン失敗の連続
  - 管理画面の URL を探す要求（間違った URL へのエラーの連続）
  - 業務時間外の管理者ログイン
  - 決済処理のエラーの多発（カード番号を総当たりする「クレジットマスター」）
  - 会員ログイン失敗の連続
  - 通常の画面の流れでは起きない要求
  - 身に覚えのないプラグインのインストール
- **データ**
  - 身に覚えのない管理者
  - 不自然な会員（メールアドレス・名前・住所）と注文
  - テンプレートやページ・ブロックに埋め込まれた不審なスクリプト

**`bin/security.sh check` がこれを見ます**（読むだけ。既定は直近 7 日、`--days=30` で変えられる）。

| 見るもの | 要確認にする条件 |
|---|---|
| 管理者 | 2 段階認証が OFF の稼働中のメンバー、最近作られたメンバー |
| 管理画面のログイン（本体のログイン履歴） | 失敗が 10 件以上、業務時間の外の成功（`.env` の `SECURITY_HOURS`。既定 `8-21`）。これまで使われていない IP からの成功は参考 |
| 会員・注文 | 名前・住所・メールアドレス・電話・注文のメッセージに、タグ・`javascript:`・`{{`・URL が入ったもの |
| ページ管理の `<head>` のタグ | スクリプトや外部の URL。最近変えたものは要確認、前からあるものは参考 |
| プラグイン | 最近入ったもの。無効のまま置いてあるものは参考（使わないなら `bin/plugin.sh remove`） |
| git に入っていない変更 | `app/` と `html/user_data/` の変更全部。外のスクリプトや難読化らしいものを含むファイルには印を付ける |
| nginx のログ | レート制限に当たった要求、ログインの送信が 30 回を超えた IP。管理画面や設定ファイルを探す要求は参考 |

管理画面が書いたファイル（テンプレート・ページ・ブロック・CSS・JS）は git で追っているので、身に覚えのない書き換えは
「git に入っていない変更」に出ます。自分で画面から直したものは git に入れておけば、次から出ません。

終わりの値は、要確認なしが 0、要確認ありが 2、見られなかったものがあると 1 です。毎朝流して、0 でなければ知らせるようにします。

```cron
0 7 * * * cd /path/to/myshop && bin/security.sh check > var/security-check.log 2>&1 || <知らせるコマンド>
```

見ていないものもあります。**決済のエラーの多発**は、決済プラグインごとにログの場所が違うので、決済サービスの管理画面で見ます。
nginx のログはサーバーに 50MB ほどしか残らないので、長く見るなら外へ出します（[監視](monitoring.md)の「ログをサーバーの外へ出す」）。

**AI にログを読ませるとき**（ガイドラインは日次を勧めています）:

- 入力が学習に使われない設定・契約で使う（使う前に必ず確かめる）
- ログに個人情報やパスワード・API キーが入っていないかを先に見る。アクセスログには IP と URL
  （検索語や注文番号を含む）が入ります
- 何のシステムのどのログかを先に伝える。リスクを示された箇所は、続けて深掘りさせる

## 4. 自分のコードを AI で診断する

EC-CUBE 本体は公式が直します。**お店が足したコード**（`app/Customize`、`app/Plugin` の自作・受託のプラグイン、
`app/template` の上書き）は、お店の側で診断します。ガイドラインの要点は次のとおりです。

- 性能の高いモデルを使い、できれば複数のモデルで診断する
- ソースコードが学習に使われない設定で使う
- 「全部のファイルを読んで診断する」と明示する（言わないと読み飛ばすことがある）
- 結果は毎回ファイルに残す。キットなら `var/` の下（git に入らない）に置き、関係者にだけ渡す
- 指摘が本当に攻撃できるかを確かめ、直し方も出させ、重大なものから直す

## 5. 不審な兆候が見えたら

ガイドラインの 3 つ（閉じる・専門家に連絡・調査が終わるまで開けない）を、キットではこうやります。

### 1. 閉じる

```bash
bin/security.sh close          # お客さんには「メンテナンス中」を出し、調査用の控えを取る
bin/security.sh close --hard   # 管理者のアカウントが乗っ取られた疑いがあるとき。入口（nginx）ごと止める
```

**メンテナンス表示のあいだも、管理画面は開いたままです**（本体の作り）。管理者のアカウントが乗っ取られている
疑いがあるなら `--hard` にします。サイトは外から見えなくなります。

`close` は、ログ・git の状態・`check` の結果を `var/incident/<日時>/` に控えます（個人情報を含みます）。DB とファイルも
控えるなら、続けて `bin/backup.sh` を打ちます（調査用。戻すためではありません）。

**`docker compose down` はしないこと。** コンテナを消すと、その中のログ（nginx のアクセスログを含む）も消えます。
閉じているあいだは `bin/deploy.sh` と `bin/publish.sh` が止まります（止めた nginx を起こして、店が開いてしまうため）。

### 2. 専門家に連絡する

侵入の経路と影響の範囲を決めるには専門の知識が要ります。**連絡先は、何も起きていないうちに決めておきます。**
渡すものは、`close` が控えた `var/incident/<日時>/` と、気づいたことの時刻つきのメモです。

### 3. 調査が終わるまで開けない

ガイドラインの再開の条件は「根本原因の特定」「攻撃者の足場の除去」「認証情報の再発行」「ログによる再侵入の
モニタリング設定」「監視の強化」です。キットで足場と認証情報に当たるのは次のものです。

- **足場**: 身に覚えのない管理者（メンバー管理）、プラグイン（`bin/plugin.sh list`）、`git status` に出る変更
- **認証情報**
  - 管理者全員のパスワード
  - `.env` の `DB_PASSWORD`・`DB_ROOT_PASSWORD`
  - `TUNNEL_TOKEN`（Cloudflare で作り直す）
  - メールの送信の鍵（`MAILER_DSN`）
  - 決済サービスの API キー
  - サーバーの SSH 鍵
- **`ECCUBE_AUTH_MAGIC` は変えないこと。** 全パスワードのハッシュの鍵で、変えると会員も管理者も誰もログイン
  できなくなります。

開けるときは、プロジェクト名を打って確かめてから開けます。止めた nginx も起こします。

```bash
bin/security.sh open
```
